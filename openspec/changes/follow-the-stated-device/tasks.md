- [x] 5.3 Verify an agreeing random source produces no diagnostic, whether it agrees because both were stated or because both followed the process. Assert the **absence of a warning**, with `pytest.warns(None)` or by capturing the logger, not merely the absence of an exception: a test that only checks nothing raised would pass against code that warns on every call, which is the vacuous form this scenario is most at risk of. Recorded with `warnings.catch_warnings(record=True)` rather than the `recwarn` fixture, which Hypothesis refuses to reuse across generated inputs
- [x] 5.4 The model builds its own random source where the work is, rather than on the host regardless. `inverse` and `inverse_coeff` construct `torch.Generator().manual_seed(42)` with no device today, so under a stated accelerator the library trips 5.1's refusal against a source the caller never supplied. Both gain a device argument like the other entry points, and build the source on the resolved device. Verify the refusal cannot fire when the caller supplied nothing, and that the existing behaviour is unchanged when nothing is stated.

  **Amended:** neither method gains a device argument. The inverse solve runs inside the regressor, against support vectors the regressor already holds, so the only device the draw can use is `self.regressor.device`. A stated device would have to be either ignored or applied by moving the regressor, and a method that silently relocates the model it was given is the side effect this change exists to remove. The draw is therefore placed on the regressor's device -- which is itself resolved from the process default when the regressor was built, so a caller who pins the process still gets what they asked for -- and the `.to(self.regressor.device)` that followed it is gone, being now a move to where the tensor already is. The source the library builds for itself is built on that same device, so the refusal cannot fire against a choice the caller did not make.

  Found while writing the test: `MultiRegression.device`'s setter only rebinds `_device` and does not move the fitted support vectors, so flipping the device after `fit` raises `X1 and X2 must have the same device type`. Pre-existing and out of scope here; the test states its device when the regressor is built instead

## 6. The application states its device

- [x] 6.1 The benchmark script states the device it runs on rather than inheriting whatever the last import left. Verify it runs with all four datasets and both operators -- the configuration that fails today with `RuntimeError: Expected a 'cuda' device type for generator but found 'cpu'`, because an operator import sets a process default the script never asked for. **Verified:** all four datasets and both operators complete, on `--device cpu` and again on `--device cuda`.

  **Correction to the approach:** stating the device once with `torch.set_default_device` at startup does not survive the run. `deepxde` is imported lazily inside `DeepONetOperator.fit`, so it resets the process default *after* the first dataset is built, and the second dataset is then generated on `cuda:0` against a host generator. The script therefore states the device by passing it -- to every generator it builds, every `generate` call and every query grid -- and sets no process default at all, so no later import can move it.

  Three defects surfaced only under this run and are fixed here: the benchmark's own GRF sampler took no `device`, and the library built several derived intermediates from the process default rather than from the data they meet
- [x] 6.2 Verify the metrics are unchanged within what was measured: identical to about six significant figures, `r2` moving in its last digit only (0.081452 against 0.081453). A larger move is a finding to chase, not a tolerance to widen. **Verified on `--device cpu`:** `mse` 0.001031, 0.026906 and 0.000202 all unchanged, and `r2` reads 0.081452, one of the two values the measurement recorded. No metric moved.

  **`--device cuda` is not a reproduction of that table and must not be read as one.** The same seed on a different device draws different numbers, so it generates a different dataset: `mse` moves to 0.001446, 0.019587 and 0.001126, and one `r2` reads -12.44 against 0.081452. That is a different sample of the same problem, not a regression, and the seed spread recorded in design.md is the scale it should be judged against. Anything reported in the paper must state the device it was generated on
