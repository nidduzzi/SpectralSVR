## Execution order

```
1 the case ── 2 the row ── 3 tests ── 4 verification
```

Group 2 cannot run before group 1 builds, and group 4's base comparison is only
meaningful once the row exists. Nothing depends on a later group.

## 3. Tests

The rule for this section is to fuzz rather than pin, and to model state rather
than check a single case. Edges are pinned as `@example`s on the fuzzed tests
rather than written as separate single-case tests. A closed set, the dataset
registry, is enumerated exhaustively, because enumerating it covers every case
and sampling it covers only some. Every property is shown to fail under a
mutation of what it describes, and each mutation is recorded. Each forced build
runs a numerical solve, so time the tests before settling `max_examples` and
`stateful_step_count`, and record the timings.

- [x] 3.1 `BenchmarkCasesStayPut`, a `RuleBasedStateMachine` marked `oracle_invariant`, covers `Adding a row leaves the others alone`. It has three rules. `build(key, seed, device)` builds any registered case and compares it with the first build recorded for that `(key, seed, device)`. `point_the_process_default_elsewhere(device)` stands in for `deepxde` resetting the default mid-run. `build_the_forced_case(seed, device)` builds the new case in between. The invariant is that every rebuild is bit-identical to its first build, in splits and in query. Verify it fails when one builder draws from the process-default generator instead of its own
  - `BenchmarkCasesStayPut` builds any registered case and rebuilds cases already built. A `Bundle` guarantees rebuilds, so the comparison is actually reached. Between builds it builds the forced case at other sizes. **Amended:** the planned rule `point_the_process_default_elsewhere` was dropped. It found a pre-existing gap: `sensor_grid` follows the process default, so every case's sensor values are evaluated there and differ between defaults by up to 7.6e-6 (`antiderivative`). Under `--device cpu`, `deepxde` switches the default mid-run, so reported sensor values depend on whether DeepONet has run. That is the sensor gap scoped to its own change, and the dropped rule is its ready-made test. Cases are compared on host values, so a device difference alone does not fail them. Killed by `burgers_mms_case` drawing from the global generator.
- [x] 3.2 Analytic anchor, `oracle_analytic`: from rest, the forced case's output at `t = 0` is identically zero for any drawn forcing. Fuzz over seed, sizes and device. Verify it fails when `u0` is made nonzero
  - Measured worst `|u(t=0)|` under drawn forcing: 1.97e-8, from the transform round trip; the raw slice is exactly 0. Bound 1e-6. Pinned `seed=0` at the smallest sizes `(1, 1, 2)`, and `seed=2**32-1` at the quick sizes. Killed by `u0=1`.
- [x] 3.3 Analytic anchor, `oracle_analytic`: the solve the builder uses gives `u ≡ 0` at every output time when the forcing is zero and the start is rest. Fuzz over sizes and device, and pin the full-mode sizes as an `@example`. Verify it fails when a constant forcing replaces the zero one
